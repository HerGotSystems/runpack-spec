ABSTRACT

RunPack defines a structured, portable task packet format that lets software delegate intelligence to the user's own AI without embedding an AI runtime, calling an external API, or depending on a specific model vendor. An app generates a packet. The user runs it with ChatGPT, Claude, Gemini, a local model, or a future system. The result can be pasted or imported back. No owner API burn. No model lock-in. No hosted inference requirement.

RunPack is the public name for the former AIP Protocol. AIP identifiers and fields remain as the v1.x compatibility layer and must not be deleted from existing packets during this transition.

§ 1

Motivation & architecture

1.1 — The problem with embedded AI

Almost every AI-powered application today follows the same model:

APP → API → AI PROVIDER → RESPONSE → USER

This creates cost, lock-in, brittleness, and privacy concerns. Small public tools often do not need hosted inference. They need a clean handoff format.

1.2 — The RunPack model

RunPack inverts the assumption. The app does not run AI. It makes a task packet that the user's AI runs.

OLD STACK
User
App
API
AI provider
Response
→
RUNPACK STACK
User + their AI
RunPack task packet
Any AI model
RunPack result packet
App reads result

The user's AI becomes the compute layer. The app becomes a packet generator and result importer.

1.3 — Design principles

  • Portable: a packet can move between apps, models, and manual workflows
  • Model-agnostic: valid packets should work with any sufficiently capable AI
  • Human-readable: users can inspect, copy, edit, and understand packets
  • Automatable: packets can be copy-pasted or passed through bridge tools
  • Open: the format is freely readable, implementable, and forkable
END § 1
§ 2

Packet format

RunPack defines task packets, result packets, and retry packets. JSON mode is recommended for app integration. Block format remains useful for human-readable copy-paste workflows.

2.1 — JSON task packet

{
  "runpack_version": "1.1",
  "legacy_aip_version": "1.1",
  "aip_version": "1.1",
  "packet_type": "runpack_task",
  "task_id": "lyrics-007",
  "task": "lyrics",
  "input": {
    "theme": "Schrödinger's Fuck",
    "tone": "dark humour"
  },
  "rules": ["return_only_lyrics", "no_preamble"],
  "output_format": "json"
}

2.2 — Block format

=== RUNPACK_TASK ===
version: 1.1
legacy_aip_version: 1.1
aip_version: 1.1
packet_type: runpack_task
task_id: npc-001
task: npc_dialogue

input:
  player_message: "I lost the boat."

rules:
  return_only_npc_reply
  no_explanation

output_format: text
=== END_RUNPACK_TASK ===

2.3 — Required fields

FieldRequiredDescription
runpack_version / versionYesPublic RunPack version string.
legacy_aip_version / aip_versionYes in v1.x transitionCompatibility fields for existing AIP parsers.
packet_typeYesUse runpack_task, runpack_result, or runpack_retry.
taskYes for task packetsTask type identifier.
task_idRecommendedApp-generated unique string.
inputUsuallyPrimary data the AI operates on.
output_formatYestext or json. markdown is reserved for v1.2 — must not be used in v1.1 packets. Parsers encountering it should treat it as text and log a warning.
rulesRecommendedConstraints on AI behaviour. Rules are free-form strings — RunPack enforces no canonical vocabulary. Apps define their own conventions; snake_case is conventional but not required. Parsers must pass rules through to the AI without modification.

2.4 — Result status values

StatusMeaning
okTask completed. Result is usable.
partialTask completed but result may be incomplete. Accept only if the receiving app can operate correctly with incomplete data. Otherwise treat as E03 and retry with a reduced payload.
refusedModel declined to execute. Result body contains reason if available.
errorExecution failed. Result body contains error information.
END § 2

§ 4

Error handling & retry protocol

V1.1

AI models may return malformed results, preamble, truncated output, or refusals. Apps should validate before importing.

CodeNameRetryable
E01Format violationYes
E02Preamble contaminationYes
E03TruncationYes, with reduced payload
E04RefusalNo
E05Type mismatchYes
E06Empty resultYes

Retry packet

{
  "runpack_version": "1.1",
  "packet_type": "runpack_retry",
  "retry_for_error": "E02",
  "original_task_id": "lyrics-012",
  "attempt": 2,
  "correction": "Return only the requested JSON. No preamble.",
  "original_task": "[verbatim original packet]"
}

§ 5

Versioning discipline & governance

RunPack uses two-part integer versioning: MAJOR.MINOR. During the v1.x transition, packets should include both RunPack and legacy AIP version fields.

  • RunPack public name: the human-facing name of the standard
  • AIP compatibility layer: retained field names and identifiers for existing parsers
  • Breaking changes: reserved for MAJOR increments
  • Steward: EMVY CHECK holds editorial control over the canonical v1.x spec
COMPATIBILITY RULE

Do not delete old AIP fields yet. RunPack is the public name. AIP remains the compatibility layer.

END § 5
§ 6

Context persistence & stateful tasks

RunPack is stateless by default. Stateful sequences may include session_id, turn, history, and history_summary.

{
  "runpack_version": "1.1",
  "packet_type": "runpack_task",
  "task": "npc_dialogue",
  "session_id": "game-sess-0042",
  "turn": 3,
  "history_summary": "Player intends to visit the abandoned lighthouse tonight.",
  "input": { "player_message": "What happened there?" }
}
END § 6
§ 7

Trust model & safety

SECURITY NOTICE

RunPack packets are prompts. Any untrusted string inserted into a packet without boundary handling is a potential prompt-injection vector.

  • Wrap user-provided text in explicit data boundaries
  • Never concatenate raw user input into rules or trusted context
  • Strip or escape packet delimiters from user input
  • Validate model output before importing it into an app

RunPack does not govern authentication, data residency, model-side safety filters, or whether a user edits a packet before running it. User agency is intentional.
